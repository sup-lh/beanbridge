# 从录音豆到 Codex：实验记录

记录日期：2026-11-14；整理与补充：2026-11-15。以下区分实际观察、来源中的声明和未实现的设计，不把静态代码推断当作真机结果。

## 起点与最终结果

最初的问题是：能否用 reverse-engineer-anything（REA）技能，把配合 iPhone 飞书使用的安克录音豆变成 Codex 的实时麦克风？

实际完成了两条链路：

1. **麦克风桥**：录音豆 → BLE → 解码 → BlackHole → Codex 原生语音输入。
2. **按键助手**：实体键 → BLE 音频 → 本地转写和浮窗预览 → 再按实体键 → 指定 Codex 对话队列。

第二条链路最终收到了真实自动投递的消息。它不点击 Codex 界面，也不需要原生输入框处于焦点状态。它始终发往配置的对话，不跟随当前窗口。

## 调查路线

### 先检查官方通路

[飞书官方说明](https://www.feishu.cn/hc/zh-CN/articles/445044627145)描述了手机 App 直连、实时转写和录音同步。Mac 的音频设备列表里当时没有录音豆。这只能证明它当时没有作为系统输入设备出现，不能据此断言硬件永远无法实时取流。

### REA 用在发行产物上

先对已安装飞书的妙记 JavaScript 包进行有范围的静态检查。单个压缩模块触及 30 秒分析预算，返回部分证据；这次没有得到可用于证明录音豆接入能力的完整功能分析，也没有把超时当成“不支持”。

之后找到 [OpenBean](https://github.com/imraywang/openbean) 及其公开协议与 Swift 实现。对完整开源代码的阅读直接使用普通源码工具；REA 用于检查下载的发布包结构。OpenBean 发布包的校验、开发者签名和公证通过，只证明所下载产物的身份与系统验签结果，不等于本项目完成全面安全审计。

这一步最有价值的变化是复用已有协议，而不是从手机 App 或固件重新逆向一遍。REA 技能是调查流程和工具入口，本身不是录音豆驱动。

### 从只读发现开始

第一次扫描没有找到设备。用户临时关闭 iPhone 蓝牙并唤醒录音豆后，Mac 找到设备，成功建立 GATT 连接并读取 04.92 固件状态。没有解绑、重置或升级设备。

上游公开测试固件是 04.82；本次 04.92 的兼容性来自随后实际录音、解码、回放与按键测试，不是通过版本号相近推断。

## 关键踩坑及处理

| 现象 | 实际原因或证据 | 处理与经验 |
|---|---|---|
| 扫描找不到设备 | 手机连接断开后即可发现 | 测试前让手机飞书释放连接；无需解绑 |
| 用户按键录音后黄灯自动熄灭 | 当时运行的是由程序开始和结束录音的诊断工具 | 明确区分“程序控制”和“实体按键控制”，每次试验只保留一个控制者 |
| 诊断工具拿到旧录音 | 设备已在录音，没有新文件事件，工具回退到列表第一项 | 取消不安全回退；只在状态明确为空闲时开始，只接受本次唯一新增文件。误读的本机临时副本已清理，设备原录音未删除 |
| 飞书虚拟设备能回传，却不出现在输入选择中 | Core Audio 查询 `DeviceCanBeDefaultDevice` 返回 0 | 设备可枚举、可采集、可设为默认输入是不同能力 |
| ESHOW 能选但测试音没有回传 | 回传测试得到零信号 | 未假设所有虚拟声卡都等价，改用 BlackHole |
| BlackHole 安装后需重启 | 安装器明确要求，重启后系统列表出现设备 | 保留用户已保存工作的重启流程，加载后再验真实输入链路 |
| FFmpeg 子进程启动后卡住 | 在终端环境中进行设备检测时，子进程被作业控制暂停 | 使用 `-nostdin`、空标准输入和有界的启动等待 |
| Swift 编译器无法推导长数组拼接 | Ogg Opus 头部的一串 `+` 表达式触发类型检查超时 | 拆成明确的追加语句，字节含义不变 |
| 系统中文语音识别显示可用，却不能完成授权 | 命令行测试被 TCC 终止，独立应用授权请求又超时 | “能力可用”不等于运行授权成功；保留结论为未解决，改用 whisper.cpp |
| 浮窗首次启动卡住 | 采样显示主线程停在读取目标配置的文件操作 | 文件读取移到后台，配置与模型移到 Application Support |
| 新应用蓝牙状态长期未知 | 没有自动授权弹窗，手动加入蓝牙允许列表后连接成功 | 通过系统设置授权并重启应用；不改隐私数据库 |
| ASR 有错字 | 小模型对专有名词与短语误听；加入词汇提示改善合成样例 | 预览是可修订结果，最终稿仍可能有错字；未做准确率统计 |
| 入队不代表已经送达模型 | CLI 成功返回、队列可读，但当前回合仍在运行 | 分开验证“入队”“对话出现”“开始处理” |

## 端到端证据

这些是当前聊天中实际观察到的测试摘要，不是人工构造的演示成绩。

| 检查 | 观察 | 可以证明什么 |
|---|---|---|
| 新建实时录音 | 连续接收约 20 秒音频，1017 个分片、缺失 0；解码为 48 kHz 单声道 Opus，20.34 秒 | 当前硬件可以实时取流并解码 |
| 用户试听 | 用户确认听到自己的测试句且清楚 | 解码结果是本次真实声音 |
| 虚拟声卡 | 测试音回传及真实声音回传成功 | 软件音频可以进入可采集的虚拟设备 |
| Codex 麦克风输入 | 对话收到“安可豆语音接入测试成功。” | 录音豆 → BlackHole → Codex 的语音输入成功；“安可”体现识别误差 |
| 实体键识别 | 按键开始、结束，浮窗显示转写；用户说明自己说的内容与结果大致相符 | 实体事件和本地识别流程可工作；没有足够原文用于测准确率 |
| 实体键入队 | 浮窗显示“按键发送测试。”，只读查询在指定会话队列中找到同一内容 | 指定目标入队成功 |
| 实时预览 | 用户确认第二次按键前已经出现文字 | 预览发生在录音期间 |
| 真正收到 | 对话收到“这是测试看看能不能直接发送?”，同时浮窗显示同一句已入队 | 按键助手的消息最终被当前对话消费 |

未逐条验证来源的其他聊天消息不被当作录音豆的独立证据。原始音频、完整聊天、私人设备信息不会为了证明实验而进入 Git。

## 当前代码验证

- 真机验证：上述两条链路、按键、预览、用户回听和最终消息投递。
- 构建：两个 Swift release 产品可构建；上游 BLE 封装存在一处 Swift 并发兼容警告，未靠放宽断言或超时掩盖。
- 自动测试：录音空闲状态、唯一新增文件选择、按键事件解析、工具路径选择，共 4 项通过。
- 仓库化修改：常见路径与环境变量选择、模型 SHA-256 检查、目标会话只读验证和 shell 语法检查通过。
- 这些测试不覆盖全天稳定性、异常断线恢复、多设备切换、ASR 质量或所有 Codex 版本。

## 可以复用的工作方法

2026-11-15 补充：找到并手动验证了官方 ⌘⌥L “复制聊天深层链接”命令。用户切换两个已有对话时分别得到不同的真实 ID，一个与当前代理会话一致，另一个通过只读查询确认存在。这给自动选目标提供了明确来源；完整后台自动触发仍未验证。详见 [上下文路由设计](context-routing.md)。

1. 先验最关键的真实链路：设备 → 声音 → 可播放 → 应用识别 → 消息投递。
2. 先用只读信息确认设备和状态；不要把文件列表第一项当作本次录音。
3. 将按键事件、音频数据、识别文字、队列回执分别留证，避免一项成功替代整体验收。
4. 有公开协议和源码后先复用，把逆向资源留给确实未知的行为。
5. 硬件链路故障时复用已经通过的证据，只回归改动的环节。
6. 将已验证原型和未来构想分开写，尤其是“当前显示的对话”和“后台最近活跃的对话”。
